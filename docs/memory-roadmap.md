# Roadmap: новые типы памяти

> **Статус: реализовано (C1–C5).** Все пять типов памяти из этого документа
> добавлены. Разделы ниже сохранены как архитектурная справка (модель данных,
> хранилище, точка интеграции); вместо статуса «предлагаемая сущность»
> указано, что реально сделано. Документ фиксирует, как устроена расширенная
> память, чтобы будущие доработки опирались на готовую реализацию.

Текущая система памяти покрывает: транскрипты дней, саммари/заголовки дней,
хронику кампании, ключевые события (вкл. «вечные»), NPC-карточки с памятью,
квесты, открытые нити, состояние партии, автосохранение боя — **плюс пять
новых типов ниже**: карта/локации (C1), игровое время/окружение (C2),
лут/экономика (C3), состояние мира (C5), фракции (C4).

---

## C1. Карта / локации — ✅ реализовано

**Проблема.** `location` раньше — свободная строка у персонажа. Нет связей
между местами, нет понятия «обнаружено / посещено», мир «плоский»: бот не может
сказать, как добраться из Морага в Чёрный Лес и через что придётся пройти.

**Сущность.**
```
Location {
  id, campaignId, name, slug
  description?            // что видно/известно
  connections: [{ to: locationId, via?, discoveredDay? }]
  discoveredDay           // когда впервые нашли
  visitedDays: number[]   // дни, когда партия там была
  current?                // true, если партия там сейчас
}
```

**Хранение (устарело: был выбран MD по паттерну NPC — заменено SQLite).** Раньше
MD-файлы `data/campaigns/<slug>/locations/<slug>.md` (frontmatter = профиль,
тело = описание/заметки); теперь — таблица `locations` в `data/campaigns.db`
(`agent/lib/campaigns/locations.ts`, singleton `locationStore`). `current` — один
на кампанию (при установке снимается с остальных).

**Интеграция.** Секция `### Карта` в авто-блоке памяти
(`agent/instructions/campaign-context.ts`): текущая локация + известные связи.
Тулы: `upsert_location`, `move_party` (ставит `current`, добавляет день в
`visitedDays`, пишет в транскрипт), `list_locations`. Chronicler обновляет при
закрытии дня. Тесты: `test/locations.test.ts`.

## C2. Игровое время / окружение — ✅ реализовано

**Проблема.** Был только `currentDay` (целое число). Нет времени суток, даты в
мире, погоды, фаз луны. Нет атмосферности и нет механических влияний: ночь не
даёт скрытных бросков, шторм — помехи на проверки.

**Структура.** Поля на `Campaign` (`agent/lib/campaigns/types.ts`):
`timeOfDay` (morning/day/evening/night), `inGameDate` (строка по календарю мира),
`weather?`. Хранятся в SQLite как колонки `campaigns` (`time_of_day`/
`in_game_date`/`weather`, миграция idempotent `ALTER TABLE`). `advanceDay`
сбрасывает `timeOfDay = "morning"`.

**Интеграция.** В авто-блоке памяти — строка «Игровое время: вечер, 3 день
Месяца Туманов; пасмурно» (`environmentLine`). Тулы: `advance_time` (циклит
`timeOfDay`, при переходе через полночь предлагает `advance_day`), `set_weather`.
**Реальные механические модификаторы** в движке (`agent/lib/engine/dnd5e.ts`):
`environmentModifiersForCheck` (ночь → помеха на зрительные проверки, преимущество
на скрытность; туман/плохая видимость → помеха на зрительные) и
`environmentModifiersForAttack` (сильный ветер/шторм → помеха на дальние атаки);
`combineAdvantage` реализует правило 5e (преимущество + помеха → обычный бросок).
Тулы `skill_check`/`combat` читают campaign, применяют окружение и поясняют его в
выводе. Тесты: `test/dnd5e-environment.test.ts`, расширено `test/store*.test.ts`.

## C3. Лут / экономика — ✅ реализовано

**Проблема.** `gold` — число у персонажа; истории нет. Нельзя узнать «откуда у
нас этот меч» или «на что мы потратили 50 золотых в день 3». Экономика
непрозрачна.

**Структура.** Append-only журнал — таблица `ledger_rows` в `data/campaigns.db`
(по паттерну key-events):
```
{ day, type: found | spent, itemOrGold, by?, note? }
```
Строка: `- [День 3] найдено: серебряный кинжал (Дэн) — пояснение…`.
Функции в `agent/lib/campaigns/journal.ts`: `appendLedgerRow` (дедуп по eventId),
`readLedger` (фильтр по дню/типу, хвост), `readLedgerRaw`.

**Интеграция.** Журнал не грузится в авто-блок целиком (растёт); доступ через
`search_memory` (keyword-поиск) и тул `list_ledger` (фильтр по дню/типу, лимит).
**Авто-запись детерминированно из тулов**: `grant_character` дописывает золото/предметы
как `found`, `complete_quest` — квестовую награду. Chronicler'у отдельный шаг не нужен.
Тесты: `test/ledger.test.ts`.

## C4. Фракции / отношения NPC↔NPC / репутация — ✅ реализовано

**Проблема.** Отношения раньше только NPC→PC (`attitude` в карточке NPC).
Фракций нет, отношений между NPC нет. Политические сюжеты (два клана враждуют,
репутация у гильдии) невозможны — мир не моделируется.

**Структура.** Сущность `Faction { id, campaignId, name, slug, description?,
standing: number, createdAt, updatedAt? }` (репутация партии: -5..+5).
`NpcProfile.relationships` остался `Record<string, NpcRelationship>` — ключом
может быть и имя фракции (без структурного изменения).
Хранение (устарело: был выбран MD по паттерну NPC — заменено SQLite): раньше
`data/campaigns/<slug>/factions/<slug>.md`; теперь таблица `factions` в
`data/campaigns.db` — `agent/lib/campaigns/factions.ts`, singleton
`factionStore`. `adjustStanding` клампит в -5..+5.

**Интеграция.** В авто-блоке — секция `### Фракции` с текущим standing.
Тулы: `upsert_faction`, `adjust_standing`. Связь с квестами: `complete_quest`
принимает `factionSlug` (или берёт `quest.giverNpcSlug`) и детерминированно
корректирует standing (completed → рост по сложности, failed/abandoned → падение).
Тесты: `test/factions.test.ts`.

## C5. Состояние мира / последствия — ✅ реализовано

**Проблема.** Ключевые события — журнал моментов (append-only), а не живое
текущее состояние мира. «Кто сейчас мёртв», «какой город сожжён», «какие
решения приняты» — всё это размазано по саммари и key-events. Мир не реагирует
на прошлые решения последовательно: бот может «оживить» убитого NPC.

**Структура.** Перезаписываемое (не журнал!) состояние мира — таблица
`world_changes` в `data/campaigns.db` с актуальными фактами мира:
```
## Погибшие
- Ян (день 1) — найден у ручья
## Изменения
- Деревня Мораг: на persuade (день 2) — староста благодарен
```
`agent/lib/campaigns/world-state.ts`: `upsertWorldChange` (идемпотентно по
категория+текст, обновляет день), `readWorldState`, `renderWorldState`.

**Интеграция.** Грузится в авто-блок памяти целиком (секция
`### Состояние мира`, кап `WORLD_STATE_CAP = 1500`). Тулы: `record_world_change`,
`list_world_state`. Связь с NPC: при смене статуса NPC на `dead` тул `upsert_npc`
авто-дублирует факт в категорию «Погибшие». Chronicler обновляет при закрытии дня.
Тесты: `test/world-state.test.ts`.

## Приоритизация (предложение)

Все пять пунктов реализованы. Порядок реализации (по убыванию сложности входа):

- **C2 (время/окружение)** — самый простой вход, мало данных, заметная
  атмосферная польза.
- **C1 (карта)** — средняя сложность, высокая ценность для исследования.
- **C3 (лут)** — низкая сложность, в основном авто-лог в `grant_character`.
- **C5 (состояние мира)** — средняя сложность, решает конкретный класс багов
  («оживление» мёртвых).
- **C4 (фракции)** — самая сложная, нужна только когда появятся политические
  сюжеты.

## Общие принципы для всех пунктов

- Вся память кампаний живёт в одной SQLite-базе `data/campaigns.db` (см.
  `AGENTS.md`). C1/C4/C3/C5 — таблицы `locations`, `factions`, `ledger_rows`,
  `world_changes`; C2 — поля на `Campaign` (нужны в движке для механики),
  колонки `campaigns` (`time_of_day`/`in_game_date`/`weather`).
- Новые секции добавлять в `buildMemoryBlock` (`campaign-context.ts`) с
  разумными капами; растущие журналы (ledger) не грузить целиком — через
  `list_ledger` / `search_memory`.
- Chronicler обновляет новые типы памяти при закрытии дня (шаги 8–10 в
  `agent/subagents/chronicler/instructions.md`); outputSchema расширена счётчиками
  `locationsUpdated` / `factionsUpdated` / `worldChangesWritten`.
- Тесты на временной SQLite-базе (`test/helpers.ts`), без `.env`:
  `test/locations.test.ts`, `test/factions.test.ts`, `test/world-state.test.ts`,
  `test/ledger.test.ts`, `test/dnd5e-environment.test.ts`, расширены
  `test/store-sqlite.test.ts`.
