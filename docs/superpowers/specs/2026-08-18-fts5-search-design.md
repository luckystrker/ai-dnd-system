# FTS5-апгрейд поиска по памяти кампании

Дата: 2026-08-18
Статус: реализовано

## Цель

Улучшить `search_memory` (agent/lib/campaigns/search.ts): текущий поиск —
подстрочный JS-скан всех строк кампании по AND-семантике («каждый терм обязан
встречаться дословно»). Проблемы:

1. Нет совпадений по словоформам («прокляти» не находит «проклятие»).
2. Полный скан таблиц в JS на каждый запрос — O(N) чтение всех строк кампании
   при росте транскрипта.
3. Нет ранжирования: результаты сортируются только по свежести дня.

Решение: полнотекстовый индекс **FTS5** (встроен в SQLite — ноль новых
зависимостей) для трёх «журнальных» (append-only, самых объёмных) таблиц:
`transcript_entries`, `key_events`, `ledger_rows`. Остальные семь источников
(NPC, локации, фракции, персонажи, квесты, состояние мира, кампания) — это
небольшие структурированные таблицы с UPDATE'ами (upsert-паттерны), их
JS-скан оставляем как есть.

## Принятые решения

- **Одна FTS5-таблица на все три журнальных источника** (а не три параллельных —
  у них идентичная структура `(id, campaign_id, day, line)`):

  ```sql
  CREATE VIRTUAL TABLE IF NOT EXISTS fts_journal USING fts5(
    source UNINDEXED,      -- 'transcript_entries' | 'key_events' | 'ledger_rows'
    source_rowid UNINDEXED,-- rowid исходной строки (для удаления из индекса)
    campaign_id UNINDEXED, -- фильтр по кампании
    day UNINDEXED,         -- сортировка
    line,                  -- индексируемый текст
    tokenize = 'unicode61'
  );
  ```

  Обычная FTS5-таблица (не external-content, не contentless): текст хранится в
  индексе, сниппеты читаются прямо из него. Удалённые кампании не всплывают:
  фильтр `campaign_id = ?` идёт по хранимой колонке (корректность; строки
  удалённых кампаний физически остаются в индексе — косметический расход,
  код удаления кампаний сейчас отсутствует).
- **Синхронизация: инкрементальный catch-up + AFTER DELETE-триггеры.**
  catch-up при каждом поиске доиндексирует строки `id > last_source_id`
  (id — глобальный AUTOINCREMENT, не зависит от кампании); счётчик — таблица
  `fts_meta(source TEXT PRIMARY KEY, last_source_id INTEGER)`. Триггеры
  (DDL в самом search.ts, модули-владельцы не трогаем) — только на DELETE
  трёх журнальных таблиц, удаляющие строку из индекса по `source`+`source_rowid`:
  этого требует миграция `migrateKeyEventDedup` (journal.ts:152 удаляет
  дубликаты key_events, journal.ts:154 делает UPDATE event_id — UPDATE не
  трогает индексируемый текст `line`, поэтому UPDATE-триггеры не нужны).
  Порядок инициализации журнала и FTS не важен: если миграция прошла до
  первого catch-up — индексируются уже почищенные строки; если после —
  DELETE-триггеры вычистят индекс. UPDATE строк `line` в журнальных таблицах
  в коде нет (инвариант, зафиксирован в рисках).
- **MATCH-запрос: кавычки + префикс**: каждый терм превращается в
  `"терм"*` (фраза с префиксом — валидный FTS5-синтаксис; звёздочка СНАРУЖИ
  кавычек: `"терм*"` молча даёт ноль результатов), термы склеиваются `AND`.
  Это сохраняет нынешнюю AND-семантику и добавляет морфологию
  («прокляти*» матчит «проклятие»/«проклятия»). Кавычки обезопашивают термы,
  совпадающие с операторами FTS5 (`AND`/`OR`/`NOT`).
- **FTS — ускоритель, не замена**: если FTS для источника дал ноль результатов
  или запрос упал с ошибкой — источник доискивается старым JS-подстрочным
  сканом (гарантия: регрессии относительно текущего поведения нет, включая
  совпадения внутри слова, которые префиксные токены не ловят: «эль» → «Каэль»).
- **Единая семантика perSource**: оба пути (FTS и JS) берут perSource самых
  свежих совпадений источника (сортировка по дню по убыванию, затем по id по
  убыванию). Старый JS-путь брал первые в rowid-порядке (= самые старые) —
  выравниваем, чтобы поведение не зависело от того, какой путь сработал.
- **Итоговая сортировка и лимиты без изменений**: день по убыванию, затем
  источник (как сейчас); `perSource`/`limit` — та же семантика. В FTS-запросе
  сортировка/лимит уходят в SQL (`ORDER BY day DESC, rowid DESC LIMIT
  perSource` по хранимым колонкам — работоспособность проверена эмпирически;
  если на целевой сборке не сработает — материализуем и сортируем в JS).

## Архитектура

Все изменения — в `agent/lib/campaigns/search.ts` (модуль уже владеет поиском).

### DDL (лениво, при первом поиске)

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS fts_journal USING fts5(...);  -- см. выше
CREATE TABLE IF NOT EXISTS fts_meta (
  source TEXT PRIMARY KEY,
  last_source_id INTEGER NOT NULL DEFAULT 0
);
CREATE TRIGGER IF NOT EXISTS fts_journal_delete_transcript AFTER DELETE ON transcript_entries BEGIN
  DELETE FROM fts_journal WHERE source = 'transcript_entries' AND source_rowid = OLD.id;
END;
CREATE TRIGGER IF NOT EXISTS fts_journal_delete_key_events AFTER DELETE ON key_events BEGIN
  DELETE FROM fts_journal WHERE source = 'key_events' AND source_rowid = OLD.id;
END;
CREATE TRIGGER IF NOT EXISTS fts_journal_delete_ledger_rows AFTER DELETE ON ledger_rows BEGIN
  DELETE FROM fts_journal WHERE source = 'ledger_rows' AND source_rowid = OLD.id;
END;
```

Триггеры срабатывают только на события в исходной таблице; журнальные таблицы
могут не существовать на момент создания триггеров — но DDL триггера ссылается
на исходную таблицу, поэтому при первом создании триггеры выполняются после
`CREATE VIRTUAL TABLE`, а в `ensureFtsIndex` каждый шаг обёрнут в try/catch
(таблицы-источники создаются лениво своими модулями; отсутствие таблицы —
легитимное состояние, источник просто пропускается, как сейчас).

### Catch-up (перед каждым поиском)

```ts
function ensureFtsIndex(): void
```

- Создаёт DDL. При неудаче создания fts-таблицы (нет FTS5 в сборке) ставит
  `ftsReady = false` — все три источника идут через JS-скан (поведение до
  апгрейда).
- Для каждого FTS-источника: `SELECT id, campaign_id, day, line FROM <table>
  WHERE id > ? ORDER BY id` (last из `fts_meta`, дефолт 0) → транзакция из
  `INSERT INTO fts_journal(source, source_rowid, campaign_id, day, line)
  VALUES ('<table>', ?, ?, ?, ?)` → `UPDATE fts_meta SET last_source_id =
  <последний id>`.
- Ошибку отсутствия таблицы-источника проглатываем.
- Первый catch-up после миграции проиндексирует всю историю (счётчик с 0);
  батч может быть большим на легаси-БД — одна транзакция на источник.

### Поиск

```ts
function buildMatchQuery(terms: string[]): string  // '"t1"* AND "t2"*'
function searchSourceFts(handle, campaignId, source, terms, context, perSource): MemoryHit[]
```

- `SELECT day, line FROM fts_journal WHERE fts_journal MATCH ? AND campaign_id = ?
  AND source = ? ORDER BY day DESC, rowid DESC LIMIT ?` с параметрами
  `(matchQuery, campaignId, source.table, perSource)`.
- Сниппет — существующий `snippetAround` (термы — «голые» слова, indexOf
  находит префиксное совпадение).
- dispatch в `searchSource`: `source.fts && ftsReady` → пробуем FTS; при
  ошибке или пустом результате — JS-путь (см. «FTS — ускоритель»).
- JS-путь выравнивается: кандидаты сортируются по дню по убыванию (для
  источников без дня — по id по убыванию), затем берётся perSource.

### Правки в SOURCES

У трёх журнальных источников добавляется `fts: true` (имя таблицы уже есть в
`source.table`). Остальные источники не меняются.

## Тесты (test/search.test.ts)

Существующие должны проходить без правок (семантика AND, сортировка по дню,
limit/perSource, скопинг по кампании, пустые результаты). Новые:

1. **Морфология/префикс**: запрос «прокляти» находит транскрипт дня 3
   («…снимает проклятие в часовне») — раньше пусто.
2. **Скопинг по кампании**: вторая кампания с записью про «Каэль» не даёт
   хитов при поиске по первой (фильтр campaign_id в FTS).
3. **Catch-up после дописывания**: после первого поиска (индекс построен)
   добавляется запись с новым словом («артефакт») — второй поиск её находит
   (инкрементальная индексация `id > last`).
4. **AND через FTS**: «часовня каэль» — строка без одного из термов в выдаче
   отсутствует.
5. **Fallback на JS (подстрока внутри слова)**: запрос «эль» (FTS-префикс не
   матчит «Каэль») всё равно находит Каэля через JS-скан.
6. **Юнит `buildMatchQuery`**: точная строка `"t1"* AND "t2"*` (пиннит синтаксис
   со звёздочкой вне кавычек).
7. **Свежесть perSource**: при >perSource совпадениях в транскрипте в выдаче
   только самые свежие (единая семантика путей).

## Риски и деградация

- FTS5 отсутствует в сборке better-sqlite3 → `ftsReady = false`, поведение
  идентично текущему (JS-скан).
- Инвариант «журнальные таблицы не обновляют `line`»: UPDATE в коде только в
  `migrateKeyEventDedup` (колонка `event_id`, не текст). Если появится UPDATE
  текста — нужен UPDATE-триггер или сброс индекса.
- Расхождение индекса (ручное вмешательство в БД) лечится сбросом:
  `DELETE FROM fts_meta` (или `DROP TABLE fts_journal` — пересоздастся
  следующим поиском) → следующий catch-up переиндексирует всё.
- Цифровые термы («09») префиксно матчат токены времени «09:12» — то же
  поведение, что у подстрочного JS-поиска; широких новых ложных срабатываний
  нет. Префикс 2-буквенных термов даёт широкую выдачу — тоже как раньше.
- Дублирование текста в индексе: для трёх журнальных таблиц это десятки
  КБ на кампанию — приемлемо.
