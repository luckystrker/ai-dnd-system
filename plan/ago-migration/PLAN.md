# Миграция с eve (TypeScript) на ago (Go)

Цель: бот целиком переписан на Go поверх фреймворка
[ago](https://github.com/luckystrker/ago). Схема `data/campaigns.db`
сохраняется — Go-версия открывает ту же базу без миграции данных. TS-код и
eve удаляются перед мержем ветки `ago-port` в `main`, после того как eval-набор
на Go проходит без регрессий.

## Решения (зафиксированы 2026-11-02)

1. **Полный порт**, не 1:1: вместе с портом исправляется harness (ниже).
2. **Баги из прожарки чинятся только в Go-версии**, TS не трогаем:
   - запись в память в группе: тулы записи требуют роль `dm` у автора
     текущего сообщения (`access.ts` → `resolveCampaignForWrite`), поэтому на
     ходах обычных игроков HP/лут/NPC не сохраняются;
   - летописец без identity доверяет любому `campaignSlug` из аргументов модели.
3. **«Добрый» d20 остаётся как есть** (`makeLuckyRandom`, история на сессию).
4. **История сессий eve не переносится.** Память кампаний (БД) — переносится.
5. **Модель** `deepseek-v4.1-flash`, провайдер на выбор: OpenRouter,
   OpenCode Go, нативный ключ DeepSeek (все — OpenAI-совместимый Chat
   Completions через `openai.NewOpenAICompletions` + `BaseURL`).
6. **Runware-иллюстрации** переносятся.
7. **Деплой**: VPS, long-poll, один Go-бинарь под systemd (вместо tmux + eve).
8. **Eval-набор синтетический** (реальных трасс нет): сценарии из правил
   `instructions.md` и истории `fix:`-коммитов.

## Решения владельца после ревью слайсов 0–1 (2026-11-02)

9. **id модели DeepSeek** утверждён: у нативного DeepSeek — `deepseek-flash`
   (его обслуживает DeepSeek-V4.1-Flash-1017), у OpenRouter и OpenCode Go —
   `deepseek-v4.1-flash`.
10. **`MAX_TOOL_ROUNDS=12`** по умолчанию утверждён как стартовое значение;
    уточняется после замеров на живом прогоне.
11. **Провайдер по умолчанию — OpenCode Go** (`LLM_PROVIDER=opencode-go`).
12. **Модель судьи eval — `muse-spark-1.3-contributor` через OpenCode Go**:
    тот же провайдер и ключ, что у бота; модель обслуживается Responses API
    (`https://opencode.ai/inference/go/openai/v1/responses`), поэтому судья
    собирается через `openai.NewOpenAIResponses`. Провайдер и модель
    переопределяются `EVAL_JUDGE_PROVIDER` / `EVAL_JUDGE_MODEL`; без ключа
    живой прогон с судьёй падает сразу с понятной ошибкой, офлайн-тесты
    ключа не требуют.
13. **`ErrMaxToolRounds`**: игрокам — короткий нейтральный ответ
    («DM задумался, повтори ход»), без диагностики; трасса уходит в лог,
    записанное тулами не откатывается. Реализация — слайс 5.
14. **`advance_day` доступен любому участнику кампании** (решение владельца
    после ревью слайса 4): смена дня — операция памяти, не админ-команда;
    роль `dm` остаётся только у `start_campaign`/`finish_campaign`/
    `invite_member`. Закрытие дня идемпотентно и не просит модель повторять
    `advance_day`.

## Решения владельца после слайса 5 (2026-11-02)

15. **Вехи внутри дня не запускают летописца.** Отдельного тула-летописца у
    DM нет: `chronicler` запускается только детерминированно при смене дня
    (`advance_day` → очередь закрытия). Вехи, обещания, смерти и прочие
    поворотные факты внутри дня DM пишет сам через `append_key_event`
    (`permanent: true` — только для фактов, которые должны остаться на всю
    кампанию). Это осознанное решение владельца, а не пропущенная правка:
    повторный запуск `CloseDay` среди дня закрывал бы день дважды и затирал
    качественное саммари. Находку ревью с предложением вернуть вызов
    летописца для вех не принимать.

16. **Бюджет токенов — на ход.** `TokenMonitor` сбрасывается в начале хода
    (`OnTurn`); порог `TOKEN_BUDGET` (по умолчанию 200k) ограничивает расход
    одного хода, а не накапливается за всё время жизни чата. При превышении
    модель получает просьбу свернуть сцену; уведомление не переживает сброс.
17. **Backfill старых дней.** После рестарта летописец закрывает только
    последние `DAYCLOSE_BACKFILL_DAYS` (по умолчанию 2) закрытых дня, не более
    `DAYCLOSE_BACKFILL_MAX` (по умолчанию 2) прогонов на старт. Более старые
    дни без саммари закрываются только детерминированным fallback-дайджестом:
    без LLM и без записи в состояние мира.
18. **Повышение авто-дайджеста.** Для последних 1–2 дней авто-дайджест один
    раз пробует повысить летописец. Если попытка не удалась, в саммари
    остаётся durable-маркер «повышение до саммари не удалось»: день
    окончателен и после рестарта не перезапускается. Дайджест старше окна
    возраста окончателен всегда.
19. **Блок памяти кампании пересобирается на каждый LLM-вызов** (а не один
    раз на ход): модель видит свежие HP, NPC и мир после тулов. Цена —
    инвалидация кэша провайдера по хвосту внутри хода; принято владельцем.

## Решения владельца после ревью слайса 6 (2026-11-02)

20. **Автоприсоединение.** Любой не-бот, который пишет в привязанном чате или
    топике активной кампании, автоматически регистрируется игроком через
    `AutoRegister` (максимум 6 игроков). Это делает код до гейта, без LLM.
    Когда партия полна, человек не регистрируется, а сообщение обрабатывается
    обычным путём (транскрипт, гейт, при сигнале — ход). `/join` остаётся
    явной командой с ответом; автоприсоединение его не подменяет. Строка
    промпта DM про `/invite` («anyone who writes joins automatically»)
    соответствует этому поведению.
21. **Окно follow-up гейта — 10 минут**, вынесено в
    `TELEGRAM_FOLLOW_UP_MINUTES` (1..1440). Калибровка — слайс 7; решение
    m9 «сократить окно / требовать вопрос» пока не принимается.
22. **Rate-limit.** Сообщения сверх лимита пишутся в транскрипт и видны
    модели в блоке памяти; LLM из-за них не будится. Остаётся как есть.
23. **Сбой отправки ответа.** Ход засчитан, апдейт помечается обработанным,
    повтора нет. M1 (дубли при транспортных ретраях) исправлен по
    рекомендации ревью — повторяются только идемпотентные чтения, — но это
    правило не меняет.
24. **Восстановление после рестарта без `Resume` подтверждено:** оборванный
    ход срезается до последнего чистого `ModelResponse` и начинается заново
    из durable-inbox.
25. **Дефолты слайса 6 приняты:** склейка 2.5 с, кап истории 600 событий,
    лимиты 20/10 в минуту. Калибровка — слайс 7.
26. **Слот-сквоттинг:** автоприсоединение остаётся, но появляется
    админ-команда `/kick` (код без LLM). Выполняет только участник с ролью
    `dm` в кампании чата; цель — реплай на сообщение игрока или аргумент
    `@username`. Удаляется только строка `campaign_members`; персонаж,
    транскрипт и остальная история остаются в БД. Кикнуть `dm` (в том числе
    себя) нельзя. Известное поведение: если удалённый снова напишет в чат,
    автоприсоединение вернёт его в партию, пока есть место.
27. **`/join` в завершённой кампании отказывает**, как и автоприсоединение:
    поиск идёт только по активной кампании (`anyStatus=false`), ответ —
    «В этом чате нет активной кампании…».
28. **Единый поиск кампании для команд и обычных сообщений.** `/join`,
    `/kick`, автоприсоединение и транскрипт используют
    `FindCampaignForIdentity`: сначала точный форум-топик, если не нашли —
    кампания всего чата; только активные кампании. Это убирает расхождение,
    когда обычное сообщение из топика находило чат-кампанию, а команда — нет.
29. **Состояние «привязана + setup» через API недостижимо** (привязка
    ставится только вместе с `active`, `FinishCampaign` её снимает). Оставляем
    как есть: `/join` вступает только в активную кампанию.

## Решения владельца перед слайсом 8 (2026-11-03)

39. **Граница сессии — по паузе в чате.** Сессия начинается, если с последнего
    сообщения в этом чате или топике прошло ≥ `SESSION_GAP_HOURS` (по
    умолчанию 20, валидация 1..720 в `internal/config`). Время последней
    активности живёт в SQLite: отдельная таблица `chat_activity` (ключ —
    кампания: она привязана ровно к одному чату/топику, решение 28) и
    атомарный `TouchChatActivity`, который возвращает прошлое время и пишет
    новое. Это единственный способ измерить паузу до текущего сообщения:
    `transcript_entries` времени не хранит (схема TS не меняется),
    `telegram_updates` есть только у Telegram и уже содержит текущий апдейт,
    `event_streams` переписывается компакцией и тоже содержит текущий ход.
    Время пишут ход DM (Telegram, repl, eval) и `recordTranscript`
    (сообщения, которые не будят LLM: гейт и rate-limit). Первый ход в истории
    чата — тоже начало сессии («первый ход в этом чате»), пересказывать нечего,
    но `get_game_context` и открытие сцены те же. Маркер «Начало новой сессии
    (пауза N ч)» кладётся в блок памяти первого LLM-вызова хода, держится на
    всех раундах тулов и не повторяется на следующем ходе. Промпт сокращён до
    правила «recap только по маркеру, без маркера recap нет»; текст сообщения
    игрока больше не триггер. В eval пауза задаётся данными фикстуры: `day-04`
    получает неделю, остальные кейсы — свежую активность (иначе свежая база
    выглядела бы первым ходом чата и recap шёл бы во всех кейсах). Датасет и
    скореры не тронуты. Известное ограничение: в repl фиксированная сессия без
    кампании (`Session{UserID: local}`), поэтому маркер начала сессии там не
    ставится — это режим отладки, прод (Telegram) и eval получают `CampaignID`.
40. **`quotes_roll` — продуктовая гарантия, а не метрика модели.** Код,
    дописывающий недостающие компоненты цитаты броска, остаётся включённым в
    живом eval: игроки видят именно этот результат. Гарантия считает свои
    срабатывания: сколько раз дописала цитату и какие компоненты (тул,
    `d20`, модификатор, итог, DC, вердикт, «помеха»). Счётчик пишется в лог
    хода (`dm: roll quote appended`) и в отчёт `cmd/eval` — на кейс, суммарно и
    по кейсам (`quote_appends`, `quote_cases`, `quote_parts`). Так видно, как
    часто модель пропускает цитату сама, хотя скорер `quotes_roll` проверяет
    итоговый ответ игрокам. Выключать гарантию в eval нельзя: это меняло бы
    продукт ради метрики.

## Редизайн harness (входит в порт)

| Было (eve) | Стало (ago) | Закрывает |
|---|---|---|
| «после `advance_day` всегда вызови chronicler» — правило промпта + страховочный хук | `advance_day` в коде ставит задачу летописцу (детерминированный шаг) | дни без саммари |
| HP в `gameState.party`, `combat.order` и листе SQLite; синхронизирует LLM | один источник истины — SQLite; `combat` сам пишет HP; `gameState` удалён | расхождение HP |
| каждое сообщение группы = полный ход LLM | склейка сообщений чата за окно N сек в один ход (`run.Enqueue`) + дешёвый гейт «отвечать ли» | стоимость, перехват разговора игроков |
| `ok` до обработки, нет дедупа, rate-limit выкидывает сообщения | durable inbox в SQLite с дедупом по `update_id`; превышение лимита пишется в транскрипт, но не будит LLM | потеря сообщений |
| окно 256k–900k токенов, растёт с длиной кампании | фиксированное окно ~64–128k, `compact.New(TokenTrigger)`; блок памяти — в хвосте контекста (policy), не в системном промпте | стоимость, кэш префикса |
| ошибки тулов — свободный текст / `{ok:false}` | типизированная ошибка: `code`, `retryable`, `remediation` | слепые повторы |
| лимита шагов нет (`sessionTimeoutMs: false`) | `WithMaxToolRounds`, дедлайн хода, бюджет токенов (`observers.TokenMonitor`) | циклы и расход |
| 25 файлов-копий тулов у летописца | одна Go-функция, два toolkit-а (DM / chronicler) | расхождение копий |
| летописец сам рапортует счётчики | счётчики считаются по изменениям в БД | непроверяемый отчёт |
| поведение проверяют живые игроки | `ago/eval` + регрессионный гейт в CI | регрессии промпта |

Авторизация: различаем «человек просит» и «действует DM-агент». Право на
запись в память кампании даёт **привязка сессии к чату кампании** (вычисляется
кодом), а не роль автора сообщения. Роль `dm` нужна только для
административных команд (`/startcampaign`, `/endcampaign`, `/invite`).
Slug кампании попадает в тулы через DI (`aginject`), а не из аргументов модели.

## Чего нет в ago — пишем сами

- **Telegram-канал**: long-poll (`getUpdates`), `sendMessage` с HTML и
  фолбэком на plain, `sendChatAction`, `sendPhoto`, загрузка файлов, `/join`,
  разбивка длинных сообщений, топики форума (`is_topic_message`).
- **`stream.Storage` на SQLite** (durable-история ходов + `Resume`); в ago есть
  только in-memory и Redis.
- **Драйвер SQLite**: `modernc.org/sqlite` (pure Go, FTS5 есть) — внешняя
  зависимость приложения; к ядру ago это правило не относится.
- `WithMaxToolRounds` в ago по умолчанию без ограничения — задаём явно.
- contrib-модули ago без тегов и с `replace ../..` — не используем.

## Слайсы (каждый — тесты зелёные, отдельный коммит)

0. **Каркас**: `go.mod`, `cmd/bot`, конфиг из env, выбор провайдера,
   CI (`go vet`, `go test`, сборка) рядом с текущим npm-CI.
1. **Eval-набор**: 30–50 синтетических сценариев в JSONL — агентность (не
   говорить за PC), публичные броски, `skill_check` vs `roll_dice`, бой по
   инициативе, групповая запись в память, закрытие дня, нейтральность.
   Скореры: mechanical (`ToolsCalled`, вызовы/аргументы) + LLM-judge по
   рубрике. Прогон на TS-боте — baseline (нужен ключ LLM).
2. **Движок**: порт `dnd5e.ts`, `combat.ts`, `rewards.ts` + их тесты.
3. **Хранилище**: порт `store-sqlite`, journal, npc, locations, factions,
   world-state, ledger, combat-snapshot, FTS5-поиск — на той же схеме;
   тест открытия копии существующей БД.
4. **Тулы**: 42 тула с типизированными ошибками и новой авторизацией;
   toolkit-ы DM и chronicler.
5. **Агенты**: DM (`instructions.md` через `embed`), chronicler, skills
   (`create-campaign`, `create-character`), policy блока памяти, compaction,
   лимиты, детерминированное закрытие дня.
6. **Telegram-канал**: inbox, очередь чата, склейка, гейт, форматирование,
   Runware, `stream.Storage` на SQLite.
