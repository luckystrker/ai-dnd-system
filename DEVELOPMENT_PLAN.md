# TTRPG Agent System — Development Plan

> Этот документ — план реализации для агента-разработчика.
> Принцип: требования клиента > архитектура > код.
> Клиентские требования зафиксированы и не подлежат изменению без подтверждения клиента.

---

## 1. Product Vision

Мультитенантная агентская система для ведения настольных ролевых игр. AI-агент выступает Dungeon Master (DM), ведёт нарратив, управляет миром и NPC. Игроки (1–6 человек) подключаются к комнате и играют синхронно.

Первая целевая система: **D&D 5th Edition** (упрощённые/кастомные правила, casual-подход).
Архитектура должна позволять добавлять другие системы (Mage: The Ascension, Cyberpunk и т.д.) как модули.

### 3.2 Agent Architecture

**DM Agent (оркестратор)**
- Ведёт нарратив, описывает сцены, реагирует на действия игроков
- Принимает решения о вызове сабагентов, бросках, событиях
- Имеет tools: `roll_check`, `spawn_npc`, `trigger_event`, `update_state`, `query_memory`, `describe_scene`
- Контекст формируется динамически: активные квесты + последние события + релевантные факты локации

**NPC Sub-Agents (пул)**
- Инстанцируются по требованию (когда NPC входит в зону взаимодействия)
- Получают: профиль NPC + персональную память + релевантные факты
- После сцены: сериализуют изменения памяти → засыпают
- Важные NPC: полноценный LLM-агент. Массовка (гоблины, прохожие): DM говорит за них сам или эвристики

**Rules Engine (детерминированный модуль, НЕ LLM)**
- Броски, проверки, бой, состояния
- Вызывается DM-агентом через tool call
- Возвращает структурированный результат: `{success: true, damage: 12, effect: "stunned"}`
- DM-агент превращает результат в нарратив

### 3.3 Memory Architecture

| Слой | Тип | Хранилище | Содержание |
|------|-----|-----------|------------|
| Game State | Hot, mutable | PostgreSQL | Позиции, HP, инвентарь, активные эффекты, инициатива |
| World Knowledge | Cold, append-only | Vector DB (pgvector) | Лор, карта, описания локаций, прегенерация |
| Campaign Memory | Warm, append-only | Vector DB + теги | События: кто, что, где, когда. Теги: локация, участники, важность |
| NPC Memory | Per-NPC | JSON в Postgres | Факты, которые NPC знает. Персональный срез campaign memory |
| Session Journal | Append-only | Postgres + LLM-суммаризация | Пересказ каждой сессии. Компрессия для контекста DM |

### 3.4 Event Visibility Model

Каждое событие в системе имеет тег видимости:

```python
class Visibility(Enum):
    PUBLIC = "public"          # все в локации видят
    PARTY = "party"            # только партия игроков
    PRIVATE = "private"        # конкретный NPC (npc_id)
    DM_ONLY = "dm_only"        # только DM-агент
    REGIONAL = "regional"      # все NPC в регионе (слухи)
```

Когда NPC-агент инстанцируется, ему подаются только события, которые он мог наблюдать или которые дошли через механику слухов (REGIONAL с задержкой/вероятностью).

### 3.5 Combat System

Два слоя:

**Тактический (код, state machine):**
- Инициатива, порядок ходов
- Позиции (grid или theater of the mind — зависит от системы)
- HP, состояния, укрытия
- Доступные действия для игрока (генерируются из статов)
- AI врагов: боссы — LLM-агент с тактическим промптом, массовка — эвристики

**Нарративный (LLM):**
- DM получает сухие события боя и описывает их
- Добавляет драматические элементы: реплики NPC, разрушение окружения, повороты
- Игроки могут заявлять нестандартные действия → DM интерпретирует → Rules Engine решает

### 3.6 Multi-tenancy / Rooms

- Комната = игровая сессия. Создаётся хостом (DM-человек или полностью AI).
- В комнате: до 6 игроков + DM-агент + NPC-агенты.
- Состояние комнаты изолировано. Несколько комнат могут работать параллельно.
- Мультитенантность: разные кампании/группы не видят данные друг друга.

## 5. Development Phases

### Phase 0: Skeleton & DM Core

**Цель:** Один игрок, текстовый чат, DM-агент ведёт сцену, бросает кубики.

Задачи:
1. Инициализировать проект: монорепо, структура папок, Docker Compose (Postgres + backend + frontend)
2. FastAPI: эндпоинты `/room/create`, `/room/join`, WebSocket `/ws/room/{id}`
3. React: минимальный UI — чат-комната, поле ввода, лог сообщений
4. LangChain: DM-агент с системным промптом (нарративный мастер). Tools: `roll_dice(sides, count)`, `skill_check(character, skill, difficulty)`
5. Rules Engine: базовый модуль — d10/d20 броски, успех/провал по порогу
6. Game State: схема Postgres — таблица `characters` (id, name, stats JSONB), `rooms` (id, config JSONB)
7. Подключение LLM: конфиг через env vars (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`)

**Критерий готовности:** Игрок создаёт комнату, пишет действие, DM отвечает нарративом, при необходимости кидает кубик и описывает результат.

---

### Phase 1: Game State & Campaign Memory

**Цель:** DM помнит контекст, мир имеет состояние.

Задачи:
1. Схема: `game_state` (room_id, state JSONB — позиции, HP, инвентарь), `events` (id, room_id, timestamp, type, payload JSONB, visibility, tags[])
2. Event Bus: все изменения состояния пишутся как события. DM-агент читает последние N событий при формировании контекста
3. Campaign Memory: pgvector — эмбеддинги событий, поиск по релевантности. Tool для DM: `recall(query, filters)`
4. Контекст DM-агента: динамическая сборка — системный промпт + последние события + релевантная память + текущий game state (сжатый)
5. Session Journal: по команде `/end_session` DM генерирует суммаризацию, сохраняет как событие типа `journal`

**Критерий готовности:** DM помнит, что произошло 20 событий назад. Может ответить "что мы делали в прошлый раз". Состояние персонажей персистентно между сессиями.

---

### Phase 2: NPC Sub-Agents

**Цель:** Важные NPC имеют собственное поведение и память.

Задачи:
1. Схема: `npc_profiles` (id, room_id, name, personality, goals, memory JSONB), `npc_states` (npc_id, location, status)
2. NPC Lifecycle Manager: spawn (при входе в зону) → inject context → active → serialize memory → despawn
3. NPC-агент (LangChain): системный промпт из профиля + персональная память + релевантные события (filtered by visibility)
4. DM tool: `consult_npc(npc_id, context)` — вызывает NPC-агента, возвращает реплику/решение
5. Visibility enforcement: NPC получает только события, которые мог видеть. Механика слухов: REGIONAL-события доходят с задержкой

**Критерий готовности:** Игрок разговаривает с NPC. NPC помнит прошлые взаимодействия. NPC не знает того, чего не мог видеть. После ухода игрока NPC "засыпает".

---

### Phase 3: Combat Module

**Цель:** Боевые сцены работают как тактическая система с нарративной обёрткой.

Задачи:
1. Combat State Machine: инициатива → ходы → разрешение действий → конец боя. Хранится в `game_state`
2. Rules Engine (D&D-модуль): броски на попадание (d20 + модификаторы vs AC), урон, состояния, упрощённая магия (слоты заклинаний → эффект → спасбросок)
3. Enemy AI: массовка — эвристики (атакуй ближайшего, отступи при HP < 20%). Босс — LLM-агент с тактическим промптом
4. DM-интеграция: боевые события подаются DM как структурированные данные, DM генерирует нарратив
5. Frontend: панель боя — порядок инициативы, HP-бары, доступные действия, лог

**Критерий готовности:** Бой на 3 врага + 1 босс. Игроки видят свои действия, DM описывает происходящее, босс принимает осмысленные решения, бой завершается корректно.

---

### Phase 4: Visual Interface & Multiplayer

**Цель:** Полноценный UI с визуальными элементами, до 6 игроков.

Задачи:
1. Multiplayer: несколько WebSocket-соединений на комнату, синхронизация действий, очередь (кто первый заявил действие)
2. Visual Board: карта локации (изображение), токены персонажей/NPC, перемещение
3. Character Sheet: статы, инвентарь, HP, активные эффекты — реактивная панель
4. Прегенерация ассетов: при создании кампании DM генерирует описания локаций → ImageGen для карт → сохранение в Asset Store
5. Режимы интерфейса: переключатель "только чат" / "визуальный режим"

**Критерий готовности:** 4 игрока в комнате, видят карту, перемещают токены, чатятся, DM ведёт игру. Визуальный и текстовый режимы работают.

---

### Phase 5: Voice & Polish

**Цель:** Голосовой ввод/вывод, UX-полировка.

Задачи:
1. STT: Whisper (или аналог) — игрок говорит → текст → DM
2. TTS: DM-ответ → озвучка (любой TTS API)
3. Стриминг: DM-ответ стримится токенами в UI (не ждать полной генерации)
4. UX: уведомления, индикатор "DM печатает", звуковые эффекты (опционально)

**Критерий готовности:** Игрок говорит в микрофон, DM отвечает голосом. Стриминг текста работает.

---

### Phase 6: D&D System Module & Multi-system

**Цель:** Полноценный модуль D&D 5th Edition + абстракция для других систем.

Задачи:
1. System Module Interface: абстрактный класс `GameSystem` — методы `roll_check`, `resolve_combat`, `get_character_template`, `get_narrative_tone`
2. D&D 5e Module: упрощённые правила — базовые классы (воин, маг, плут, жрец), упрощённые заклинания (без полной книги), advantage/disadvantage, без строгой математики
3. Narrative Tone Module: системный промпт-аддон для DM — лексика, темп, тропы (для D&D: высокое фэнтези, подземелья, драконы, героические приключения)
4. Campaign Preset: прегенерация мира D&D — локации, фракции (Гильдия Магов, Орден Паладинов, Гильдия Воров), NPC-заготовки
5. System Switch: при создании комнаты выбирается система → подгружается модуль правил + тон

**Критерий готовности:** Полная партия по D&D 5e (3-4 сессии). Правила работают, тон выдержан, DM не ломается. Можно создать комнату с другой системой (хотя бы заглушка).

## 7. Key Architectural Decisions

| # | Решение | Обоснование |
|---|---------|-------------|
| AD1 | Rules Engine — чистый код, не LLM | Детерминизм, отсутствие галлюцинаций в механике |
| AD2 | NPC lifecycle: spawn/despawn | Экономия токенов, масштабируемость |
| AD3 | Event-sourcing для campaign memory | Append-only, аудируемость, простой поиск по тегам |
| AD4 | pgvector вместо отдельной векторной БД | Минимум инфраструктуры, один Postgres на всё |
| AD5 | Visibility на уровне событий | Естественное поведение NPC, без "всезнающих" персонажей |
| AD6 | LLM через OpenAI-совместимый интерфейс | Любой провайдер, ноль привязки |
| AD7 | Combat = state machine + LLM-нарратив | Тактика не галлюцинирует, описание живое |
| AD8 | Системные модули (GameSystem interface) | Мульти-системность без переписывания ядра |
| AD9 | Контекст DM собирается динамически | Не вливать всю историю в промпт — только релевантное |
| AD10 | Frontend: режимы (чат / визуал) | Требование клиента R2 |

## 8. Constraints & Notes

- Правила D&D 5th Edition — кастомные, упрощённые. Не воспроизводить книгу правил. Ориентир: casual, нарратив важнее математики.
- Голос (Phase 5) — не блокирует остальное. Можно играть без него.
- Прегенерация ассетов (карты, изображения) — на этапе создания кампании, не в рантайме.
- Все агентские вызовы стримятся. Игрок не должен ждать > 3 секунд без фидбека.
- Документ обновляется по мере принятия новых решений.

## 9. Definition of Done (для всего проекта)

Группа из 4 игроков подключается к комнате, DM-агент ведёт партию по D&D 5th Edition на протяжении минимум 3 сессий. DM помнит контекст, NPC ведут себя осмысленно, боёвка работает, визуальный интерфейс отображает карту и состояния. Правила упрощённые, тон выдержан, никто не скучает.
